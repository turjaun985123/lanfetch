# ADR-002: Web Server — Harden the Existing std-TcpListener Server in Place

**Status:** Accepted (V2 Wave 1, integrator arbitration) · **Date:** 2026-11-27 · **Deciders:** Chief Architect, Squad 5 lead

**Context.** `lanfetch-web` serves the embedded UI and API from a hand-rolled HTTP server on `std::net::TcpListener` (`desktop-tauri/web/src/serve.rs`, 816 lines): thread-per-connection, byte-at-a-time header parsing, `POST /api/<cmd>` dispatch mirroring the 24 Tauri commands, SSE at `/api/events`, poster serving from the engine cache, static files exclusively from the compile-time embedded `dist`. Wave 0 (Agent 5) found real flaws: no socket read/write timeouts (slow-loris pins a thread forever), unbounded connection/thread count, no authentication (see ADR-003), no `Host`/`Origin` validation, no security headers, no API versioning. Crucially, every one of those flaws is a *missing guard*, not a structural defect: routing, dispatch, SSE fan-out, and traversal-safe static serving (paths are never percent-decoded into the filesystem; `..` is rejected) are sound. The brief (Squad 5) asks us to *evaluate* Axum/Actix, and also forbids unnecessary dependencies and fashionable replacements.

**Decision.** Harden `serve.rs` in place during Wave 3: (1) socket read/write timeouts on every connection; (2) a bounded connection semaphore with a documented cap and refusal on overflow; (3) request body limits retained (1 MB) and header cap retained (64 KB), plus a per-connection request deadline; (4) token authentication per ADR-003; (5) `Host` header allowlist check on loopback binds; (6) security headers on responses (`X-Content-Type-Options`, a CSP matching the desktop one, no-cache for API); (7) versioned routes per ADR-005 (`/api/v1/…` with the legacy `/api/<cmd>` shape kept as a compatibility adapter); (8) structured JSON error bodies with stable error kinds. No new runtime dependency is added.

**Alternatives considered.**
- *Axum (tokio):* mature routing/middleware and async I/O, but pulls the tokio runtime into a binary whose entire selling point is a small, dependency-light, single-file artifact (CI even asserts `ldd` shows no GUI libs); forces an async rewrite of the dispatch path that currently calls the synchronous engine directly; thread-per-connection at LAN scale (a handful of clients) is not a measured bottleneck. Rejected: cost and dependency weight buy nothing the hardening list doesn't.
- *Actix Web:* same async-runtime cost, larger surface, no advantage over Axum for this workload. Rejected.
- *Minimal blocking framework (e.g. tiny_http):* replaces the parser honestly but still requires re-implementing SSE fan-out and the dispatch adapter, and adds a dependency to save ~200 lines of working code. Rejected.

**Consequences.** Positive: the binary stays std-only beyond the engine's existing deps; every fix is a small, testable diff against known code; the Wave 0 security findings close without a transport rewrite; CI integration tests can target the real server binary. Negative: we remain owners of an HTTP parser — mitigated by the existing caps, the new timeouts, malformed-request tests in the Wave 3 regression suite, and a written rule that any future protocol need beyond HTTP/1.1 + SSE reopens this ADR. Thread-per-connection remains — bounded by the semaphore, acceptable for the documented LAN scope, and recorded as a known limit in SECURITY.md.
