# ADR-003: Web Authentication — Per-Install Bearer Token for Non-Loopback Binds

**Status:** Accepted (V2 Wave 1, integrator arbitration) · **Date:** 2026-11-27 · **Deciders:** Chief Architect, Squad 5 lead, Squad 10 (security)

**Context.** Today `lanfetch-web` has no authentication anywhere. Bound to loopback (the default) that is defensible but not airtight — any local process, and any website via DNS rebinding, can reach it. Bound with `--lan` (the mode the phone use case requires) it is, per Wave 0 Agent 5, **unauthenticated full remote control**: start downloads of attacker-chosen URLs, delete files, rewrite settings, repoint the server list — by any device on the network. The brief (Squad 5, Part 12) requires authenticated remote control and forbids assuming a private LAN is trustworthy. Constraints: the primary client is the user's own phone browser on the same LAN; there is no account system and no cloud; the token must survive restarts (re-pairing a phone after every reboot is a non-starter); the desktop (Tauri) transport is IPC and out of scope.

**Decision.** A per-install random token: 32 bytes from the OS CSPRNG, generated on first run, persisted as `web-token` (0600 permissions) in the engine data dir alongside `settings.json`. Rules: (1) **Non-loopback binds require the token on every `/api/*` route** (reads and writes) — `Authorization: Bearer <token>`; only `/api/v1/health` is exempt, and the embedded-UI assets themselves are served unauthenticated (they contain no data). The served page obtains the token from the URL fragment the server prints (`http://host:8787/#t=<token>`) on startup and in the desktop Settings screen, stores it in `sessionStorage`, and attaches it to API calls; the fragment is never sent to the server or logged. (2) **Loopback binds are exempt from the token** but gain a `Host` allowlist check (`127.0.0.1`, `localhost`, `[::1]`) to blunt DNS rebinding. (3) A "Reset web access token" action in Settings regenerates the token, invalidating phones until they open the new link. (4) SSE authenticates via a query token on the EventSource URL (accepted only for the events route), documented as the single exception, because `EventSource` cannot set headers. (5) Failed auth returns 401 with no detail; 256-bit entropy plus the connection cap from ADR-002 bounds guessing.

**Alternatives considered.**
- *Password (user-chosen, hashed):* familiar, but users pick weak ones, it needs a set/change UI, a hash dependency, and storage of a verifier — more machinery protecting less entropy than a generated token. Rejected.
- *Pairing code (short-lived 6-digit code exchanged for a session):* best phone UX in theory, but adds a pairing protocol, expiry state, and session storage to a single-user LAN tool; the printed-link-with-fragment flow achieves the same one-tap outcome with none of the state. Rejected for V2; may return if multi-device management ever becomes a requirement.
- *Session-cookie exchange after pairing:* adds cookie/session state for no gain over `sessionStorage` + Bearer at this scale. Rejected for V2 (noted as the one point where SECURITY.md's draft differed; this ADR wins).
- *mTLS / client certificates:* strongest, and completely disproportionate — enrollment on a phone browser is hostile UX. Rejected.
- *No auth, document the risk:* the Wave 0 verdict makes this untenable for a mode we ourselves instruct users to enable. Rejected.

**Consequences.** Positive: `--lan` becomes safe to recommend; the token is unguessable, revocable, and survives restarts; loopback stays zero-friction; no new dependency (CSPRNG from OS sources reachable via std on the shipped targets; if a target proves otherwise, Wave 3 justifies any tiny addition in its commit). Negative: the startup output and Settings must present the link carefully (a token in a screenshot is a leaked token — the UI masks it behind a reveal action); SSE's query-token exception is a deliberate, documented wart; existing `--lan` users must open the new link once after upgrade — called out in release notes and MIGRATION.md. The bootstrap flow is covered by Wave 3 security regression tests (401 matrix, Host check, token reset).
