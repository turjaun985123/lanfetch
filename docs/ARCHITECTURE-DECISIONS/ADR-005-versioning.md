# ADR-005: Versioning — Product 2.0.0 and Persisted-Format Forward-Compatibility Rules

**Status:** Accepted (V2 Wave 1, integrator arbitration) · **Date:** 2026-11-27 · **Deciders:** Chief Architect, Integration Director

**Context.** The product ships as 1.6.0 from **four** files that must agree: `desktop-tauri/package.json`, `package-lock.json`, `src-tauri/Cargo.toml`, `engine/Cargo.toml` (plus `web/Cargo.toml`), with `tauri.conf.json` deferring to `package.json`, the .deb Version derived from Cargo, and CI asserting the .deb identity. Wave 0 (Agent 10) found the discipline good but manual — four hand-bumped files, nothing enforcing equality except the .deb gate — plus two drifts: Android's `versionName` is already 1.3.10 in source against a published 1.3.9, and the release workflow embeds the literal string "LanFetch 1.6.0" in its notes, guaranteed to go stale (Wave 1 fixes the string to derive from the tag, and corrects its false "upgrades are automatic" claim — there is no updater plugin). Separately, Agent 8 found the persisted formats are one innocent change away from data loss: `Settings` fields and `PersistedTask` have almost no `#[serde(default)]`, so adding a required field tomorrow makes today's files unparseable, and the load fallback then silently resets *all* settings or drops the *entire* download queue.

**Decision.** (1) **V2 ships as product version 2.0.0** across desktop and web (the transformation is user-visible: new lifecycle behavior, authenticated LAN mode, versioned API). The four-plus version files are bumped in the Wave 9 release commit only — waves do not churn versions. (2) A CI version-consistency check (extending the existing frontend job's check) fails the build unless `package.json`, the Cargo manifests, and the release-notes template agree. (3) Android keeps its independent version line (next release 1.3.10, resolving the existing drift by shipping it, documented in MIGRATION.md) — Android and desktop versions are *not* forced to converge. (4) **Persisted-format rules, effective Wave 2 and binding on all squads:** every new field on a persisted struct (`Settings`, `PersistedTask`, sources, favorites) ships with `#[serde(default)]` or an explicit migration; enums gain a catch-all fallback rather than failing the parse; a file that fails to parse is **never** silently replaced by defaults — the existing `.bak` fallback stays, and total parse failure surfaces as a visible error state with the original file preserved under a `.broken-<timestamp>` name; every format change adds a round-trip test loading a fixture written by the previous release. (5) The HTTP API is versioned independently of the product: `/api/v1/` per ADR-002, bumped only on breaking contract change.

**Alternatives considered.**
- *Version 1.7.0 (minor bump):* understates a release that changes LAN-mode behavior (auth becomes required) and the download lifecycle; users deciding whether to upgrade deserve the major signal. Rejected.
- *Unify Android and desktop on 2.0.0:* Android is explicitly *not* being transformed by V2 (preservation squad); stamping it 2.0.0 would claim changes it didn't receive — the same honesty failure as the "automatic upgrades" release-notes bug Wave 0 caught. Rejected.
- *CalVer:* the project's entire history, tags (`desktop-tauri-v*`), and user expectations are semver-shaped; switching buys nothing. Rejected.
- *Schema-version field in every persisted file:* heavier machinery than serde defaults + fixtures for a single-writer local app; revisit only if a future migration cannot be expressed as defaults. Deferred, not rejected outright.

**Consequences.** Positive: one enforceable version story; the release-notes staleness bug closes; the silent-data-loss class of bug (Agent 8's Medium findings) becomes structurally impossible rather than vigilance-dependent; API consumers get an independent stability promise. Negative: the fixture discipline adds a small tax to every persistence change (one fixture file + one test per format change — accepted as cheap insurance); the 2.0.0 bump means the still-pending final `1.6.0` tag decision must be resolved explicitly at Wave 9 — either 1.6.0 ships as the redesign's final first (the RC6 acceptance already awaiting the user), or V2 supersedes it and 1.6.0 remains an RC line. That is the user's call, recorded here so it cannot be silently elided.
