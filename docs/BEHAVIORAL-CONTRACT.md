# Cross-Platform Behavioral Contract

One user-visible behaviour per operation, on every platform. "Rust today"
is the shipped 1.6.0 RC6 engine (desktop + web share it); "Android today"
is the 1.3.x app. The V2 target column is normative: a platform that
cannot meet it has a defect, not a variant.

| Operation | Expected user-visible behaviour | Android today | Rust today | V2 target |
|---|---|---|---|---|
| **Add download** | Adding a URL queues it once and starts probing; the row appears immediately as Queued. | Dedup by URL (unique index); probe runs, then pump. ✔ | Dedup on enqueue vs Queued/Running/Paused — but the check and insert are separate lock scopes, so a fast double-add can create duplicates. | Atomic dedup: a second add of the same URL returns the existing task on all platforms. |
| **Pause** | The transfer stops promptly, progress freezes at a byte-exact position, and the row shows Paused. | Coroutine + call cancellation closes the socket immediately, even mid-read; final snapshot persisted before unwind. ✔ | A flag is polled between blocking reads; a stalled read delays the pause up to the 30 s read timeout, holding its concurrency slot meanwhile. | Pause takes effect within the documented bound (≈5 s worst case on a stalled server, ~instant on a healthy one); slot released when the worker actually exits; persisted position matches bytes on disk. |
| **Resume** | A paused download continues from its on-disk position after re-validating size and validator (ETag/Last-Modified) against the server. | Resume re-probes; validator/size drift resets the plan before any bytes move. ✔ | Resume re-validates via `If-Range`; stale validator fails loudly. ✔ (for tasks that were successfully probed once) | Same, everywhere — including tasks restored after an app restart. |
| **Cancel** | Cancelling removes the task and its partial file; nothing reappears afterwards. | Remove deletes the task; service state follows the queue. ✔ (no separate Cancel state — Remove is the cancel) | Remove exists, but a running task removed at the wrong moment can still have its `.part` renamed to a finished file by its supervisor — the download "resurrects". | One semantic everywhere: Remove = cancel + delete partial; a removed task can never rename, complete, or notify afterwards. |
| **Retry a failed download** | Tapping Retry on *any* failed task re-checks the server and, if it is back, downloads. | Retry is literally `resume()`: full re-probe, plan rebuilt if needed. Always works. ✔ | **Broken for probe-failed tasks:** a failed first probe leaves `ready=false`, and `start()` refuses non-ready tasks — Retry is a permanent silent no-op; only Remove + re-add works. Mid-download failures retry fine. | Retry always re-probes when no valid plan exists and re-queues when one does. A failed task is never a dead end. |
| **Recover after crash / restart** | Reopening the app shows interrupted downloads as Paused with their downloaded progress intact and resumable. | `requeueAllRunning()` at init; segment maps read back from Room; sink reports whether partial bytes survived, else the plan zeroes. ✔ | Running/Queued restore as Paused with the persisted plan — but progress is only saved at state transitions, so a crash re-downloads everything since the last pause/failure; and a missing/truncated `.part` is not reconciled, so a task can complete with zero-filled holes. | Periodic progress checkpointing bounds loss to seconds; startup reconciles plan vs actual `.part` length before anything may resume or complete. |
| **Server without Range support** | The download proceeds single-stream and completes byte-exact; progress still reports. | Single-stream path with the same byte-count validation. ✔ | Probe sees no `Accept-Ranges` → one segment over the whole file; a 200 answer is accepted for that plan. ✔ | Unchanged behaviour; covered by a regression test on both engines. |
| **Server falsely advertising Range** | Wrong or ignored Range responses are detected; the file is never silently corrupt — it restarts single-stream or fails with a clear reason. | `Content-Range` is parsed and must match the request; mismatch throws. ✔ | Status 206 is trusted: `Content-Range` is **never validated**, so a wrong-range body is written at the requested offset and the download completes corrupt. (A plain 200 *is* correctly rejected for multi-segment plans.) | Validate `Content-Range` on every 206 before writing a byte; on mismatch, fall back or fail loudly — identical rule to Android. |
| **Server disconnects mid-download** | The transfer retries with backoff, resumes from the last written byte, and only fails after bounded attempts — showing why. | Per-segment retry, 6 attempts, exponential backoff ≤ 30 s, counter resets on progress. ✔ | Stall-based retry exists (7 no-progress attempts, backoff ≤ 4 s) — but any HTTP *status* error (incl. 429/5xx) fails the segment instantly with no retry. | One policy: transport stalls *and* retryable statuses (408/429/5xx, honouring `Retry-After`) retry with jittered backoff; permanent statuses (403/404) fail immediately with a classified error. |
| **Duplicate URL** | Adding a file already queued/downloading focuses or reports the existing task instead of starting a second transfer to the same file. | Unique index prevents a second row. ✔ | Dedup exists but races (see Add); additionally, the Detail screen resolves tasks by URL first-match, so a dead Failed row can shadow a live retry of the same URL. | Single task per URL, enforced atomically in the engine; UI lookups by task id, never by first URL match. |
| **File changed on server** | If size or validator changed since the partial download, the partial is discarded and the download restarts — never spliced. | `StaleFileException` on any validator drift; plan resets before bytes move. ✔ | `If-Range` is sent on every segment and a 200-instead-of-206 is rejected — but a server that ignores `If-Range` yet answers 206 with new content defeats it (same hole as false-Range). | Validator + `Content-Range` + total-size are cross-checked at probe, resume, and per segment; any drift restarts the task with a visible "file changed, restarted" note. |
| **Disk full** | The download fails (or refuses to start) with an explicit disk-full message; no other task's data is damaged, and already-downloaded files stay intact. | Pre-flight disk-space check in the coordinator with an explicit message. ✔ | No pre-check and no classified error: writes fail as generic I/O strings, and `write_atomic` silently swallows save failures, so on a full disk the queue stops being persisted with no signal anywhere. | Pre-flight space check when the total is known; write/save failures surface as a classified `DiskFull` error on the task and in Settings/storage; state saves failing is itself a visible warning, never silent. |
