# ADR-001: Frontend Architecture — Incremental Module Extraction on Astro + TypeScript

**Status:** Accepted (V2 Wave 1, integrator arbitration) · **Date:** 2026-11-27 · **Deciders:** Chief Architect, Squad 6 lead

**Context.** The entire frontend lives in one file, `desktop-tauri/src/pages/index.astro` (2,805 lines): five screens as `<section data-screen>` blocks, one inline module script, and 25 module-level mutable state variables (`libGen`/`feedGen`/`detailGen`, `dlFetching`/`dlDirty`, `sourcesList`/`probeMap`, `taskRows`, `pendingFileClicks`, …) with no ownership boundaries. The V2 brief (Squad 6) asks for a component architecture and names React or SolidJS as preferred candidates. Against a rewrite: the UI was redesigned and QA'd *today* (redesign waves R1–R7, 16-agent QA sweep, all findings fixed in `43ed283`); there are **zero frontend tests**, so a rewrite has no regression net; the page script is not even type-checked today (tsc cannot parse `.astro`). Part 4 of the brief explicitly permits keeping the current structure when migration would create unnecessary risk. The genuine problems are monolith size, unowned shared state, and listener/disposal discipline — not the rendering model, which already does keyed in-place patching for the hottest surface (Transfers).

**Decision.** Stay on Astro + TypeScript + Tailwind 4 + Tauri 2. Extract the page script incrementally into factory modules under `src/lib/` — `transfers.ts`, `servers.ts`, `library.ts`, `detail.ts`, `settings.ts`, `shell.ts` — each receiving the typed API client plus shell services (toast, dialog, announcer, navigation) and exposing `mount()`/`dispose()`. Introduce per-screen state objects owned by each module; the generation/stamp guards move with their screens. `index.astro` becomes a composition root: markup, sprite, and module wiring only. `api.ts`, `format.ts`, `ui.ts` survive unchanged. A framework migration may be re-proposed only after (a) extraction is complete and (b) a frontend test harness exists to catch regressions.

**Alternatives considered.**
- *React + TypeScript big-bang:* largest ecosystem, but rewrites all markup, 2,100+ script lines, dialog/toast/focus/observer machinery; React's re-render model actively fights the keyed-patching and focus-preservation behavior QA just verified; discards today's behavioral evidence. Rejected for V2.
- *SolidJS big-bang:* fine-grained reactivity maps more naturally onto current patching, but still a full rewrite of markup and state with no tests, a smaller ecosystem, and a new build integration. Rejected for V2; remains the more plausible future candidate.
- *Do nothing (keep the monolith):* zero risk today, but every V2 wave (engine events, auth UI, new settings) lands in the same 2,800-line file and the 25 shared variables keep coupling screens. Rejected.

**Consequences.** Positive: working, QA'd behavior is preserved by construction; each extraction is independently reviewable and CI-verifiable; module boundaries create the seams a later framework decision actually needs; no new dependencies. Negative: no component model, no JSX ergonomics, state discipline is by convention (factory closures) rather than framework-enforced; the `.astro` script remains outside tsc coverage until extraction moves logic into `.ts` files (extraction *fixes* this screen by screen — an underappreciated benefit). Neutral: DESIGN.md's deferred `state.ts` idea is superseded by per-module state objects; a single global store is deliberately *not* introduced.
